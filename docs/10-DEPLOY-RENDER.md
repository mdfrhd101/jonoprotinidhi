# 10. Deploying the private demo to Render (free plan)

Audience: the owner. Goal: a live, password-protected demo of the **Tarique Rahman showcase tenant** that MPs can open from their own phones, built from the public GitHub repo `mdfrhd101/jonoprotinidhi` (branch `main`), redeploying on every push.

This is a **demo**, not production. It runs entirely on free tiers (Render free web services and static site, MongoDB Atlas M0). Section 9 lists what that costs you; read it before the demo.

## 0. What you get

| Piece | Render service | URL (planned) |
|---|---|---|
| Public site, pinned to the Tarique tenant, Basic-auth + noindex | `jonoprotinidhi-demo` (web) | `https://jonoprotinidhi-demo.onrender.com` |
| API | `jonoprotinidhi-api` (web) | `https://jonoprotinidhi-api.onrender.com` |
| Admin panel (calls `/api` on its own origin; Render forwards it to the API) | `jonoprotinidhi-admin` (static site) | `https://jonoprotinidhi-admin.onrender.com` |
| Database | MongoDB Atlas M0 (outside Render) | n/a |

Everything is defined in [`render.yaml`](../render.yaml). It contains no secret value; secrets are typed into the Render dashboard once (step 5).

Deployment strategy: straight deploy of a new, private environment. Nothing real depends on it, the local database is only read, and the Atlas copy can be rebuilt at any time (step 3). Rollback is in section 10.

## 1. Before you start

1. You have accounts or are ready to create them (free, by hand: nobody can do this for you): **GitHub** (you have it), **MongoDB Atlas**, **Render** (sign up with "Continue with GitHub").
2. The code for this deployment is **committed and pushed to `main`**: `render.yaml`, `scripts/deploy/copy-db.mjs`, `docs/10-DEPLOY-RENDER.md`, the `start:prod` scripts in `apps/api/package.json` and `apps/web-public/package.json`, and the public-site changes (`middleware.ts`, `lib/demoGate.ts`, `lib/host.ts`, `lib/env.ts`, `lib/api.ts`, `app/healthz/route.ts`). Render builds from GitHub, not from your laptop. The repo is **public**: scan the commit for secrets first (CLAUDE.md rule).
3. On your laptop: local MongoDB is running (127.0.0.1:27017, database `jonoprotinidhi_dev`) and you use Node 24 (`export PATH=~/.local/node24/bin:$PATH`).
4. Keep `apps/api/.env` open in an editor. You will copy three values out of it (step 5). **Never paste them into chat, a commit, an issue or a screenshot.**

## 2. MongoDB Atlas: free cluster, network access, connection string

1. Go to <https://cloud.mongodb.com> and sign in or sign up. Accept the default organization and project (or create a project named `jonoprotinidhi`).
2. Click **Create** (or **Build a Database**) and choose **M0 / Free**.
3. Provider **AWS**. Region **Singapore (ap-southeast-1)** (closest to Render's Singapore region, where `render.yaml` places the API and public site). Name it `jonoprotinidhi-demo`. Click **Create Deployment**.
4. In the "Connect to your cluster" dialog under **Create a database user**: user name `jpdemo`, click **Autogenerate Secure Password**, **Copy** it somewhere safe for the next two minutes, then click **Create Database User**. Close the dialog (you do not need a connection method yet).
5. Left menu **Security > Network Access > Add IP Address > ALLOW ACCESS FROM ANYWHERE** (this fills `0.0.0.0/0`) > **Confirm**. Render's free services have no fixed IP, so this is required. The database password is what protects it.
6. Left menu **Database > Clusters**, click **Connect** on your cluster > **Drivers**. Copy the string. It looks like
   `mongodb+srv://jpdemo:<db_password>@jonoprotinidhi-demo.abcde.mongodb.net/?retryWrites=true&w=majority&appName=jonoprotinidhi-demo`
7. Turn it into **your URI**: replace `<db_password>` with the password, and put the database name `jonoprotinidhi` between the `/` and the `?`:
   `mongodb+srv://jpdemo:THE-PASSWORD@jonoprotinidhi-demo.abcde.mongodb.net/jonoprotinidhi?retryWrites=true&w=majority&appName=jonoprotinidhi-demo`
   If the password contains `@ : / ? # %`, percent-encode those characters. (Autogenerated passwords are safe.)

Atlas button labels move around from time to time; the intent of each step is what matters.

## 3. Copy the local database to Atlas

Do this **before** step 5 so the API starts against a filled database. From the repo root:

```bash
export PATH=~/.local/node24/bin:$PATH
node scripts/deploy/copy-db.mjs "<YOUR-URI>" --bind-host jonoprotinidhi-api.onrender.com
```

What it does: copies every collection, all documents and all indexes from `jonoprotinidhi_dev` to the Atlas database named in your URI, then verifies document and index counts per collection. It only reads your local database. It never prints the URI. It refuses to write if the target already holds documents (use `--force` to replace the collections it copies).

`--bind-host` registers `jonoprotinidhi-api.onrender.com` as a platform domain of the `tarique-rahman` tenant **in Atlas only**. This is required: the API finds the tenant from the Host header, and on Render the public site reaches the API by the API's own host name. Without it the public site shows "site not found".

Expected end of output: a table with `ok` on every row, then `done: 19 collections, 1358 documents copied and verified`.

Choices worth making now:
- The local database contains **test complaints and audit/SMS logs** from development. To start the demo with an empty complaint list, add `--exclude complaints,complaintevents,smslogs,auditlogs` (the tracking-ID counter is kept).
- The copy includes the **users** (same e-mails and passwords as local). That is how you will log in.

Other options: `--dry-run` (report only), `--force` (replace), `--bind-only` (just register a host, see step 6), `--tenant <slug>`, `--source <uri>`. Run `node scripts/deploy/copy-db.mjs --help`.

## 4. Check what Render will read

`render.yaml` should be on `main`. No edit is needed unless Render later assigns a different sub-domain than planned (step 6).

## 5. Render: create the Blueprint

1. Go to <https://dashboard.render.com> and sign in with GitHub.
2. Top right **+ New > Blueprint**.
3. **Connect a repository.** If `mdfrhd101/jonoprotinidhi` is not listed, click **Configure account** (or **+ Connect another account**) and give the Render GitHub app access to that repository (**Only select repositories**). Use this route, **not** the "Public Git Repository" URL box: only the GitHub app route installs the webhook that makes auto-deploy on push work.
4. Select the repo. Blueprint name `jonoprotinidhi-demo`, branch `main`, path `render.yaml`. Render lists the three services and asks for the values marked `sync: false`.
5. Fill them in:

| Service | Variable | What to enter |
|---|---|---|
| `jonoprotinidhi-api` | `MONGODB_URI` | your URI from step 2 |
| `jonoprotinidhi-api` | `MASTER_KEY` | copy from `apps/api/.env` (the value after `MASTER_KEY=`). **Must be identical to local**, or the copied encrypted data cannot be read |
| `jonoprotinidhi-api` | `PHONE_PEPPER` | copy from `apps/api/.env`. **Identical to local** |
| `jonoprotinidhi-api` | `SITE_SERVER_TOKEN` | copy from `apps/api/.env`. **Identical to local** |
| `jonoprotinidhi-api` | `TURNSTILE_SECRET` | demo: `1x0000000000000000000000000000000AA` (Cloudflare's published always-pass **test** secret; the API refuses to start in production without one) |
| `jonoprotinidhi-demo` | `SITE_SERVER_TOKEN` | the **same** value as on the API (type it twice, once per service) |
| `jonoprotinidhi-demo` | `TURNSTILE_SITE_KEY` | demo: `1x00000000000000000000AA` (the matching test site key) |
| `jonoprotinidhi-admin` | none | |

   Copy values exactly: no quotes, no spaces, no trailing newline.
   Generated by Render (nothing to type): `JWT_SECRET` on the API, `SITE_BASIC_AUTH_PASS` on the demo site.
6. Click **Deploy Blueprint**. The first build takes about 5 to 10 minutes. Watch each service's **Logs**. A failed API boot prints `Invalid environment: <variable>: <reason>`, which names the exact variable to fix (Service > **Environment**, edit, **Save**, it redeploys).

## 6. Confirm the real URLs

Each service page shows its URL under the name. They must be exactly the three in section 0. Render adds a suffix (for example `jonoprotinidhi-api-x1y2.onrender.com`) when someone else already owns the name. If any differs:
1. Replace the old URL everywhere in `render.yaml` (API: `PUBLIC_BASE_URL`, `CORS_ORIGINS`; demo: `API_URL`, `TENANT_HOST`; admin: `VITE_PUBLIC_SITE_URL` and the rewrite destination), commit, push.
2. Register the real API host in Atlas without redoing the copy:
   `node scripts/deploy/copy-db.mjs "<YOUR-URI>" --bind-only --bind-host <real-api-host>`
3. Update the same values in each service's **Environment** page if Render does not pick them up from the new `render.yaml` (it ignores `sync: false` values on later syncs; the plain values are updated).

## 7. First checks, in this order

1. `https://jonoprotinidhi-api.onrender.com/api/health` shows `{"status":"ok"}` (the first call may take about a minute).
2. Open the public site URL. The browser asks for credentials. User **`demo`**; password: Render > `jonoprotinidhi-demo` > **Environment** > `SITE_BASIC_AUTH_PASS` > reveal (eye icon). You should see the Tarique home page with photos and videos. Try the complaint page.
3. Open the admin URL. Sign in with your local super-admin (or MP owner) credentials; they are in `apps/api/.seed-credentials.local` (read it yourself, never paste it anywhere).
4. **First login needs 2-step enrollment** (2-step login is mandatory in production; the API refuses to run without it). After the password, the screen shows a QR code and key. Scan it with an authenticator app (Google Authenticator, Microsoft Authenticator, Authy, 1Password), type the 6-digit code, and keep any recovery codes shown. Every later login on this site asks for a current code. Enrollment is stored per user in Atlas, separate from local. **Enroll every account you plan to use in the demo the day before**, not in front of the MPs.
5. In the admin, open the Tarique tenant. The "view site" links should open the demo site.

## 8. Demo day

- Free web services **spin down after 15 minutes without traffic** and take **about one minute** to wake (the API also reconnects to Atlas). The first visitor after a pause waits, and the very first page load can show an error because the site wakes first and then wakes the API.
- **10 to 15 minutes before the demo**: open the API health URL, then the public site (click Home, About, Gallery, Complaint), then sign in to the admin. Keep a tab open.
- Do not keep the services awake all month with a pinger: Render gives the whole account **750 free instance hours per month** and two always-on web services use about 1,490, so both would be suspended around mid-month. A pinger for the demo window only is fine.
- Give the MPs the URL, user `demo`, and the password through different channels.

## 9. What the free tier costs you (known limits)

- **Files uploaded through the admin are ephemeral.** Post, banner and gallery images and videos go to the API's disk (`/tmp/jonoprotinidhi-uploads`), which Render wipes on every restart, spin-down and deploy. Consequences:
  - Tarique's existing content is unaffected: it uses only `upload.wikimedia.org` images and YouTube. **Do not upload new photos in the admin during the demo**; they would vanish after the next spin-down.
  - The fictional tenant `ndp3` has seeded local images; they will show as broken. It is not served on the public site (the site is pinned to Tarique), only visible in the admin.
  - **Citizen complaints are not affected**: voice recordings and attached files are stored inside the complaint document in Atlas, so they persist. Each complaint with attachments can be several MB, and Atlas M0 holds 512 MB in total.
  - Real fix for a pilot: object storage (S3/R2) behind `MediaStorage`, or a paid plan with a persistent disk.
- **The API URL is public.** Basic auth guards the public-site pages and noindex keeps them out of search, but the API answers its public endpoints (the same content the site shows, nothing private) to anyone who calls it directly, because the admin panel needs the API reachable. "Private" here means unlisted and not casually shareable, not secret.
- **Captcha is a dummy.** The Cloudflare test keys accept anything, so there is no bot protection on the complaint form. Fine behind a password; not for a pilot.
- **Rate limits are per visitor IP as Render's proxy reports it**; several visitors may share a bucket (complaint submissions are limited to 5 per minute per bucket). Fine for a handful of MPs.
- **Rollbacks on free services reach only the two most recent previous deploys.**
- Build minutes: 500 per month on a free workspace. `render.yaml` uses build filters so a docs-only push does not rebuild anything.

## 10. Operations

**Change something:** commit and push to `main`. Only the services whose files changed rebuild.

**Rollback:** Render > the service > **Events** (or **Deploys**) > pick the previous successful deploy > **Rollback**. For anything older, `git revert` and push. Database changes are not rolled back by this; re-run `copy-db.mjs --force` to reset the Atlas copy to your local data.

**Stop the demo:** each service > **Settings** > **Suspend Service**. Turn auto-deploy off with **Settings > Build & Deploy > Auto-Deploy: No** (or `autoDeployTrigger: off` in `render.yaml`).

**Change the Basic-auth password:** `jonoprotinidhi-demo` > **Environment** > edit `SITE_BASIC_AUTH_PASS` > **Save** (restart only, no rebuild).

**Remove Basic auth later (open the site):**
1. Delete `SITE_BASIC_AUTH_USER` and `SITE_BASIC_AUTH_PASS` from the **jonoprotinidhi-demo** service's Environment page. Optionally delete `NOINDEX` to let search engines in. **Save**; the service restarts.
2. **In the same commit, delete the same entries from `render.yaml`.** Otherwise the next Blueprint sync puts `SITE_BASIC_AUTH_USER` back, and the site then fails **closed**: with only one of the two variables set, every visitor gets 401 by design.
3. Remember that opening a real politician's site publicly needs written consent from his office (CLAUDE.md).

**Pin a different tenant:** the pinned host must be a Domain of that tenant in the database (`--bind-only --bind-host ... --tenant <slug>`) and `TENANT_HOST` must be that host. One host belongs to one tenant.

## 11. Before any real pilot: rotate and harden

This demo reuses your laptop's keys and a copy of your dev data. For a real pilot, do **not** carry it over; start clean:
- `MASTER_KEY` and `PHONE_PEPPER` protect the encrypted complainant data and phone hashes in the copy. Changing them makes that data unreadable, and there is no re-encryption tool yet. A pilot should start from a **fresh database with new keys**, not from this copy.
- Rotate: `SITE_SERVER_TOKEN` (both services at once), `JWT_SECRET` (signs everyone out), the Atlas database user password, `SITE_BASIC_AUTH_PASS`, and **every admin password** (the copied users still have their local passwords). Re-enroll 2-step codes.
- Replace the Cloudflare test keys with a real Turnstile widget (Cloudflare dashboard > Turnstile) and restrict it to the real domain.
- Move uploads to object storage; move off free tiers (no spin-down, persistent storage, real backups); put Atlas behind an IP allow-list instead of `0.0.0.0/0`.
- Add CI (GitHub Actions: `npm test`, `npm run typecheck`, `npm run bugs:check`) and switch `autoDeployTrigger` to `checksPass`.
- Keep `MFA_REQUIRED=true`.

## 12. Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| API deploy fails, log says `Invalid environment: ...` | The named variable is missing or malformed (e.g. `MASTER_KEY` must be 32 bytes base64; `SITE_SERVER_TOKEN` at least 32 characters). Fix it on the Environment page. |
| API starts, health stays 503 / deploy times out | MongoDB unreachable: wrong URI or password, no database name in the URI, or Atlas Network Access lacks `0.0.0.0/0`. |
| Public site: "site not found" or error page | The API host is not registered as a Tarique domain in Atlas: run `copy-db.mjs --bind-only --bind-host <api-host>`. Or `TENANT_HOST`/`API_URL` differ from the API's real host. |
| Public site: first load fails, refresh works | Cold start: the API was asleep (section 8). |
| Public site loops on the password prompt | Wrong user/password. Use `demo` and the dashboard value. A service with only one of the two variables set rejects everyone (section 10). |
| Admin: login says network error, or "Unexpected token <" | `/api/*` is not reaching the API: check the rewrite in the admin service (**Redirects/Rewrites** tab) and the API URL in `render.yaml`. |
| Admin: login works but you are signed out on refresh | The session cookie is not surviving Render's rewrite. Tell the engineer; the fallback is to serve the admin from the API service itself (needs an `app.ts` change). |
| Admin: "invalid code" at 2-step | Phone clock off, or code expired; wait for the next code. Use a recovery code if you saved one. |
| Images missing on the public site | Only `upload.wikimedia.org` / `thumb.wikimedia.org` and `https` YouTube are allowed. Uploaded files vanish on restart (section 9). |
| Render says the Blueprint is invalid | `render.yaml` was edited badly. It validates against Render's published JSON schema as committed; revert the change. |
